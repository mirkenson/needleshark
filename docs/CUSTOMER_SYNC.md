# Клиенты, компании, amoCRM и Unisender

## База компаний для исходящей связи — 30 октября 2026

`companies` дополнена миграцией `20261030_customer_sync_profiles.sql`: направления
(`text[]` с GIN-индексом), отметка контакта, город, деятельность, сайты, общие
телефоны/email, подробные профильные контакты, канал поставщиков, приоритетный
канал и источники. `company_profile.py` обновляет эти свойства при штатном
GET-обмене с amoCRM, включая ручную смену отметки менеджером. Снимок старше
`source_updated_at` их не перезаписывает.

`research_data` хранит выбранные исходные сведения с ключом источника, а
`offer_hints` — подсказки «Что предложить» и ID примечания CRM. Эти два свойства
не заменяются очередным CRM-снимком. Стандартные email/телефоны берутся из общих
контактов; сведения о специалистах и добавочных номерах остаются целиком в тексте.
Имена специалистов не становятся записями `customers` или контактами amoCRM.

Разовый `ops/import-companies.py` принимает проверенный JSON вне Git и отдельный
закрытый журнал. По умолчанию только сверяет компании. `--apply` создаёт недостающие
поля, дополняет компании и добавляет обычные примечания. Его клиент запрещает
запись в сделки/контакты, связи через `_embedded` и удаления. Повторы сопоставляют
точные сайты/названия и сохранённый ID; неоднозначность останавливает импорт.
Существующие телефоны, email, тексты и направления объединяются; непустой статус
менеджера, название, Web и остальные поля сохраняются. Новые компании получают
«Контакта не было», совпавшие без отметки — «Не уточнено».

POST компании/примечания заранее фиксируется в fsync-журнале. Потерянный ответ
сверяется чтением, без слепого повтора. Журнал блокируется на время запуска и
привязан к хешу входного файла. Изменённый файл требует отдельного проверенного
плана; новые варианты уже созданного мультисписка добавляются отдельно после
проверки его значений. Сохранять журнал, исходник и снимок CRM в закрытой резервной
папке VPS. Не публиковать их в Git или публичной статике.

Тесты: `test_company_profiles.py`, `ops/test_company_import.py` и расширенная
`check_customer_sync_postgres.py`. Фактический импорт, количества и проверенный
релиз фиксируются в PROJECT_CONTEXT и обезличенном отчёте. Импорт базы не является
обращением клиента, согласием на рассылку или поводом для уведомления Loop.

Решение владельца от 30 октября 2026: реализовать серверный обмен и журнал
переходов, сохранив действующую передачу заявок сайта в amoCRM. Этот документ
описывает реализованный код; фактическая установка и результаты проверок
фиксируются в `PROJECT_CONTEXT.md` и отчёте `verification/20261030-customer-sync.json`.
Письма и сценарии по этапам сейчас не запускаются.

## Потоки данных

- Форма → прежний `/api/leads` → клиент + неизменяемый снимок заявки → прежние
  очереди SMTP, amoCRM и настроенного LOOP. Создание сделки и её поля сохранены.
- amoCRM → `customer_sync.py` → компании, контакты, связи, сделки, журнал этапов.
  Этот клиент API допускает только GET. Импорт не создаёт задание исходящей очереди.
- `customers` + идентификаторы + компания + первое касание → `unisender_sync.py`
  → отдельный список «Needle Shark — база клиентов» (ID 3).
- Новые контакты Unisender загружаются с `contact_status=disabled`. Существующие
  статусы и подписки не активируются заново. Это справочник, а не запущенная рассылка.

Обратный обмен использует отдельные потоки процесса `needle-leads`; ошибки API
не откатывают приём формы. PostgreSQL и оба сетевых клиента имеют таймауты.
Импорт и приём формы используют одну транзакционную блокировку идентичности,
чтобы одновременное обращение не создало двух клиентов.

## Таблицы и владение полями

Миграция: `server/migrations/20261030_customer_sync.sql`, только добавления.

| Таблица | Что хранит |
| --- | --- |
| `customers` | Прежний ID, `company_id`, признаки теста/конфликта, полный снимок первого известного касания. Legacy `contact/contact_key` сохранены. |
| `customer_identifiers` | Email/телефоны клиента, нормализованное значение, источник и актуальность. Один общий адрес может принадлежать нескольким людям; это конфликт для автоматического экспорта. |
| `companies` | Свой ID, название, ИНН/КПП при наличии, прочие поля CRM в `details`, amoCRM ID с ID аккаунта, время версии и архив. |
| `customer_amo_links` | Соответствие контакта amoCRM локальному клиенту; несколько CRM-дублей могут соответствовать одному человеку. |
| `customer_company_history` | Предыдущая/новая компания и время получения изменения. |
| `customer_touchpoints` | Известные обращения, их источник, время, UTM, страница формы, ClientID и достоверность. |
| `crm_deals`, `crm_deal_contacts` | Отдельные сделки, текущая воронка/этап, компания, связь с исходной заявкой и контактами. |
| `crm_stages` | Названия воронок/этапов по ID; переименование не меняет идентичность этапа. |
| `deal_stage_log` | Неизменяемые записи переходов с прежней и новой воронкой/этапом, ID сделки/клиента, временем события/получения и внешним ID события. |
| `deal_latest_stage` | Представление последней записи по каждой сделке и признак `ready_for_trigger`. |
| `crm_unresolved_events` | Полученные события сделок, пока недоступных в полном списке: сохраняются и повторно обрабатываются. |
| `customer_sync_state` | Аккаунт, время включения, курсор событий, успешный цикл, безопасный код ошибки и готовность первой загрузки. |
| `customer_sync_exclusions`, `customer_sync_conflicts` | Проверенные тестовые исключения и конфликты для ручного разбора. |
| `marketing_permissions` | Разрешение на маркетинг для конкретной пары клиент/email: unknown, allowed с доказательством, withdrawn. |
| `unisender_contact_sync` | Состояние экспорта email, хеш полей, попытки, время сверки, безопасная ошибка. |

amoCRM владеет менеджерским именем, компанией и текущими сделками. Новая форма
сохраняет собственные значения в `orders` и payload, не переписывая исторические
заявки. Пустая компания в CRM не стирает известную связь автоматически. Несколько
компаний у контакта требуют разбора. Отсутствие сущности после успешного полного
обхода помечает локальное CRM-соответствие архивным; заявки и клиенты не удаляются.
Архивный клиент, у которого нет заявок сайта и активного CRM-соответствия, не
экспортируется. Это также может означать изменение доступов, не доказанное удаление.

## Дедупликация и тесты

Email: пробелы по краям удаляются, регистр не учитывается. Точки и `+suffix`
не удаляются. Телефон: цифры; российское начальное 8 в 11 цифрах приводится к 7.
В первую очередь используется сохранённое соответствие amoCRM → клиент,
затем email/телефон. Совпадение с несколькими клиентами или общий адрес у разных
CRM-людей не приводит к автоматическому слиянию: фиксируется конфликт,
связанные клиенты исключаются из Unisender. Форма при этом сохраняется.

Первый запуск переносит идентификаторы из существующих заявок. Для нескольких
CRM-карточек одного человека учитывается объединение текущих идентификаторов.
Исторические идентификаторы остаются в БД; устаревшие только-CRM значения
помечаются неактуальными. Подтверждённые формой значения сохраняются.

До первого импорта загружается закрытый список удалённых тестовых CRM ID.
Дополнительно исключаются карточки с явным начальным маркером QA/ТЕСТ/TEST,
а также контакты, связанные исключительно с исключёнными тестовыми сделками.
Общий с реальной сделкой контакт не удаляется. Клиенты с `is_test` не экспортируются.
Проверки используют новые синтетические контакты, не адреса реальных клиентов.

Очистка 30.10 удалила 28 подтверждённых тестовых заявок и 20 клиентов; сохранены
11 реальных заявок/клиентов и все 66 нецелевых строк. Это состояние на момент
очистки, не обещание неизменного числа: позднее продолжают приходить заявки.
[Отчёт очистки](verification/20261030-customer-sync-design.json).

## Первое известное касание

`customers.first_*` заполняется целиком из самого раннего известного обращения,
а не отдельными UTM от разных событий. Позднее найденное более раннее обращение
может уточнить этот снимок; история остаётся в `customer_touchpoints`.

Для сайта источник — время и поля сохранённой заявки. Для несайтовой сделки —
время создания и имеющиеся поля CRM; почтовый источник 21223 отмечается email.
Контакт CRM без сделки ещё не доказывает обращение: касание не выдумывается.
UTM/ClientID не угадываются по email или названию компании. Это первое известное
обращение, **не доказанный первый рекламный визит**: браузерная аналитика формы
может отражать последнюю кампанию в сессии. Сырые обращения/файлы и ClientID в
Unisender не передаются. Подробности: [ANALYTICS.md](ANALYTICS.md).

## Журнал этапов

Синхронизатор примерно раз в минуту получает полный список компаний, контактов,
сделок и этапов, затем события `lead_status_changed`. Курсор перекрывается на
пять минут; уникальный ID события устраняет повторы. Курсор продвигается только
в той же транзакции, что данные. Переход назад — обычная новая запись.

Реальное событие имеет `event_kind=transition` и старый/новый этап из amoCRM.
Если история недоступна или текущий снимок отличается от последнего события,
создаётся явно помеченная `baseline`/`reconciliation`, всегда `historical=true`.
Это сверка состояния, не выдуманный реальный переход. Весь доступный API журнал
читается при первом запуске, но полнота истории удалённых/недоступных сделок не
гарантируется. Их полученные события не теряются: остаются в unresolved-таблице.

Последняя запись выбирается по времени **события**, не порядку поступления.
При одинаковом времени реальный переход имеет приоритет перед технической сверкой.
Текущий этап дополнительно сверяется со снимком сделки. Если в одну секунду
есть разные новые этапы, порядок API не доказывает их последовательность:
`ready_for_trigger=false`. Архивные сделки также не готовы к триггеру.

```sql
SELECT d.customer_id, d.deal_id, d.amo_lead_id,
       d.previous_stage_id, d.new_stage_id, s.stage_name,
       d.occurred_at, d.source_event_id, d.historical, d.ready_for_trigger
FROM deal_latest_stage d
LEFT JOIN crm_stages s ON s.amo_account_id=d.amo_account_id
 AND s.pipeline_id=d.new_pipeline_id AND s.stage_id=d.new_stage_id;
```

Нельзя брать один последний лог клиента: у него могут быть несколько сделок.
Для будущего сценария брать запись конкретной сделки с `ready_for_trigger=true`,
`historical=false` и `event_kind=transition`. Само чтение последнего лога не
обеспечивает однократную отправку письма.

## Unisender и безопасность повторов

Для клиента выбирается один актуальный email (legacy основной, если актуален,
иначе упорядоченный запасной). Общие адреса и конфликтные/тестовые клиенты
пропускаются. Без email карточка остаётся в БД и amoCRM.

Поля: `Name`, `NS_CUSTOMER_ID`, `NS_COMPANY_ID`, `NS_COMPANY_NAME`, `NS_PHONE`,
`NS_FIRST_CHANNEL`, `NS_FIRST_SOURCE`, `NS_FIRST_MEDIUM`, `NS_FIRST_CAMPAIGN`,
`NS_FIRST_CONTENT`, `NS_FIRST_TERM`, `NS_FIRST_AT`, `NS_FIRST_PAGE`, `NS_PERMISSION`.
Телефон — отдельное строковое поле, чтобы не объединять контакты Unisender
по нативному телефонному ключу. Пустые значения не очищают чужие поля.

Используются getContact/importContacts с `overwrite_lists=0`, `overwrite_tags=0`.
Перед записью сохраняется состояние uncertain, после — проверяются числовой
результат каждой строки и повторный getContact. Его русские public_name
сопоставляются с техническими name через getFields. После неизвестного исхода
импорт автоматически не повторяется: сначала сверка; несовпадение остаётся на
разборе. Неизменённые подтверждённые карточки сверяются раз в 10 минут.

Глобальная или относящаяся к нашему списку отписка/блокировка отражается как
withdrawn. Импорт не делает подписанного заново из отписавшегося и не удаляет
подписки на другие списки. Метод отправки писем и API-триггеры отсутствуют в
разрешённом наборе клиента. Новые контакты disabled независимо от локального
разрешения; включение рассылки — будущая отдельная реализация.

## Эксплуатация и откат

- `CUSTOMER_SYNC_ENABLED=1` включает локальный реестр и обратный импорт.
- `UNISENDER_SYNC_ENABLED=1`, `UNISENDER_LIST_ID=3` включают экспорт справочника.
- Ключ лежит вне Git в `/etc/needle-shark/unisender.key`, root:needleleads, 0640;
  путь можно переопределить `UNISENDER_KEY_FILE`. Каталог root:needleleads 0710
  даёт группе только проход; остальные закрытые файлы остаются root 0600. В URL/журнал он не включается.
- Оба флага добавляются в существующий закрытый `leads.env`; остальные настройки
  и сервисные unit не меняются. Перед включением — резервная копия и исключения тестов.
- Установка кода/схемы: проверенный и отправленный коммит,
  `bash ops/install-server-mail.sh --upgrade`. Флаги по умолчанию выключены.
- Для остановки нового обмена выключить оба флага и перезапустить needle-leads.
  Прежняя ветка приёма форм и отправки в amoCRM остаётся доступной.
- При откате кода сначала проверить current/previous и выключить новые флаги.
  Аддитивные таблицы не удалять, дамп поверх новых заявок не восстанавливать.

Проверять свежесть `customer_sync_state.last_success_at`, `last_error`, конфликты,
`crm_unresolved_events`, состояния `unisender_contact_sync`. Секреты, имена,
email, payload и тексты заявок не писать в общий отчёт или Git. Доступ к токенам,
SMTP и CRM остаётся у прежней серверной службы. Отдельного интерфейса разбора
конфликтов и уведомлений о зависшем новом обмене пока нет.

## Что потребуется для писем по этапам

1. Таблица правил: воронка/этап или конкретный переход, шаблон, задержка,
   допустимость возврата и повторного входа. Версия правила входит в ключ события.
2. Транзакционная очередь отправки с уникальным ключом
   `(rule_version, deal_id, source_event_id)` и отдельный журнал доставки.
3. Перед отправкой после задержки заново проверить этап сделки, актуальный
   контакт, согласие, отписку, доступность email, лимит частоты и часовой пояс.
4. Правило отмены письма, если сделка уже ушла дальше или назад. Сам обратный
   переход хранится сейчас, но не означает автоматически новое письмо.
5. Webhook/обратная сверка доставки, bounce, complaint, отписки и их идемпотентная
   обработка; сейчас есть только сверка статусов контакта, не статистика писем.
6. Отдельно решить объединения CRM-карточек, несколько компаний и замену основного
   email. Старый контакт Unisender автоматически не удаляется и не переносит согласие.

API Unisender доступен отдельно от конструктора интеграций; тарифные лимиты
сервиса сохраняются. Расширение тарифа/покупки не выполнялись.
