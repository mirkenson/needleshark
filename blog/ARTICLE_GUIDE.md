# Редакционный стандарт блога Needle Shark

Владелец одобрил 14 сентября 2026 года формат статьи «Как подготовить мотоцикл и квадроцикл к зимнему хранению». Этот стандарт применяется к следующим статьям. Технические поля блоков описаны в [README.md](README.md); действующий пример — `blog/posts.json`, общий рендерер — `blog/blocks.py`.

## Как выстраивать материал

1. **Вопрос читателя.** Один конкретный вопрос в H1. Короткое введение сразу объясняет, что делать и кому пригодится материал. Без неподтверждённых обещаний, вымышленных авторов и статистики.
2. **Ориентир для чтения.** Для длинного текста — краткий `callout` с главным выводом и смысловые `heading` с постоянными `id` и короткими `tocLabel`. Оглавление формируется автоматически.
3. **Основная часть.** Последовательные шаги или смысловые разделы, короткие абзацы, списки по необходимости. Чередовать текст с полезными визуальными паузами. Не начинать каждый раздел одинаковой рекламной вставкой.
4. **Альтернативные сценарии.** Использовать `tabs`, когда читателю нужно выбрать свой вариант: место хранения, тип задачи, условия применения. Общие обязательные сведения оставить перед табами или после них.
5. **Дополнительные пояснения.** Использовать `accordion` для примеров конкретных моделей, уточнений и FAQ. Ключевые инструкции и ограничения товара остаются раскрытыми в основном тексте или `callout`.
6. **Изображения по смыслу.** Брать подходящие изделия и детали из каталога. Подпись объясняет связь с соседним текстом; чехол другой комплектации не иллюстрирует чужие свойства. Генератор переиспользует готовые адаптивные WebP и alt, не создавайте копии для каждой статьи.
7. **Следующий шаг.** Для длинной коммерчески связанной статьи минимум два CTA-блока в разных частях, обычно три. Когда уместно, включать каталог и Ozon. Для короткой заметки или темы без товарной связи не добавлять рекламу ради количества. Каждая подводка связана с текущим разделом: измерить габариты → выбрать размер; понять конструкцию → сравнить комплектации.
8. **Практический финал.** Памятка, вывод или короткий `checklist`, если читателю есть что проверять и отмечать. Не повторять весь материал. Завершить источниками, которые рендерер собирает из блоков `sources`.

Это набор приёмов, а не обязательная одинаковая последовательность для каждого материала. Не нужно вставлять все типы блоков в каждую статью. Основная мысль должна оставаться понятной при беглом просмотре и без взаимодействия с элементами.

## Оформление и достоверность

- Сохранять логотип, Manrope, цвет `#BE3E3E`, существующие отступы и компоненты. Не добавлять шрифты, отдельные стили или библиотеки для одной статьи.
- `**жирное выделение**` — для коротких ключевых фраз; `==акцент фоном==` — для редких главных выводов. Не выделять целые разделы.
- У каждого изображения содержательная подпись; изображения изделий преимущественно чёрные, подача минималистичная. Не считать визуализацию доказательством свойств или испытаний.
- Проверяемые факты сопровождать `sources` сразу после относящегося фрагмента, в том числе внутри пояснений. Читать первичный источник, сохранять ограничения модели и года выпуска. Рендерер делает сноски, общий список и обратные ссылки.
- Не скрывать в аккордеоне оговорку, от которой зависит покупка. Совместимость, комплектацию, размеры, цены и коммерческие показатели брать из подтверждённых данных каталога/владельца.
- `date` — фактическая дата первой публикации, `updated` — фактическая дата изменения. Существующие slug, ID заголовков и CTA сохранять.

## Блоки и измерение действий

У интерактивных блоков задавать постоянный `id` (например, `storage-place`, `battery-care`, `storage-checklist`). Копировать структуру, а не чужие тексты и идентификаторы CTA внутри той же статьи. Пример табов:

```json
{
  "type": "tabs",
  "id": "storage-place",
  "title": "Где будет стоять техника?",
  "items": [
    {"label": "В гараже", "blocks": [{"type": "paragraph", "text": "Согласованный совет для гаража."}]},
    {"label": "Под навесом", "blocks": [{"type": "paragraph", "text": "Согласованный совет для навеса."}]}
  ]
}
```

Это пример структуры для подготовки черновика, не текст для публичной статьи. Для `accordion` используется такой же набор `title`/`items`/`label`/`blocks`; для `checklist` — `title` и список текстовых `items`. HTML в строках не разрешён. Новые блоки добавлять в общий рендерер только при реальной необходимости.

Счётчик 112428810 наследуется из шаблона. CTA используют `blog_cta_click` с article/cta/page. Табы, аккордеоны и чек-лист — существующую цель `ui_click` с article/element/block/item/state; программное раскрытие при переходе по сноске не считается отдельным взаимодействием. Оглавление, сноски и источники размечаются автоматически. Номера пунктов интерактивного блока соответствуют порядку `items`; при существенной смене их смысла учитывать это при сравнении отчётов.

Внешние ссылки получают UTM через общий генератор. Для Ozon обязательна одна `utm_campaign=vendor_org_211216`, source=`needle-shark.ru`, medium=`referral`, различимый content. Внутренние ссылки не получают UTM, чтобы сохранялся источник привлечения посетителя. Не подменять успех заявки кликом: `lead_submitted` возникает только после подтверждения сервера. Где смотреть результаты и какие ограничения остаются — [ANALYTICS.md](../docs/ANALYTICS.md).

## Подготовка к публикации

Проверить факты и ссылки, сгенерировать страницы по README, выполнить тесты и `ops/check-site.py`. Проверить в браузере 360/390/768/1024/1440 px, изображения, клавиатуру, табы, аккордеоны, оглавление, сноски и возврат, CTA и связанные формы. Проверить события с локальной подменой SDK, затем после публикации — настоящий счётчик и отчёт. Размечать проверочные визиты отдельной QA-кампанией.

Публиковать проверенный и отправленный в GitHub коммит через `ops/deploy.sh` в рамках разрешения владельца. После публикации проверить публичный HTTPS и записать подтверждённые результаты в `docs/PROJECT_CONTEXT.md`. При недоступности внешней площадки или отчёта прямо указывать ограничение проверки.
